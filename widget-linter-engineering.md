## 1. Принципы

1. **Корректность раньше скорости.** Линтер, который быстро ошибается, хуже медленного, но точного. Любая оптимизация должна сохранять вывод байт-в-байт (подтверждается golden-тестами).
2. **Измерять, а не гадать.** Вход ограничен (виджет ≤ 32 КБ, жёсткий потолок 1 МБ), поэтому большинство «микрооптимизаций» не даёт ничего. Время съедают парсинг, zlib и запуск процесса. Любое утверждение «так быстрее» подкрепляется бенчмарком в PR.
3. **Невозможное состояние — непредставимо.** Типы кодируют инварианты: сырые строки и числа не гуляют по API (`RuleId`, `Span`, `Severity`, `Confidence`, `Profile`).
4. **Ядро чистое.** Нет ввода-вывода, часов, сети, глобального изменяемого состояния, случайности. Ядро — функция `(&[u8], &Config) -> Report`.
5. **Никаких паник на пользовательском вводе.** Ввод недоверенный. Паника — это баг уровня security.
6. **Детерминированность.** Один вход и конфиг → один и тот же байтовый вывод, на любой платформе и в любой оболочке.
7. **Данные вместо кода.** Правила и профиль — данные; код правил тонкий. Это снижает объём кода и вероятность ошибок.
8. **Маленькая поверхность API.** Публично только то, что нужно. Всё остальное `pub(crate)`.
9. **Автоматизируй дисциплину.** Всё, что можно проверить машиной (форматирование, lints, лицензии, semver, размер WASM, регрессии производительности), проверяется в CI. Люди ревьюят дизайн, а не пробелы.

## 2. Окружение и конфигурация workspace

### 2.1. Тулчейн

- `rust-toolchain.toml` фиксирует канал (`stable`) и компоненты (`rustfmt`, `clippy`, `llvm-tools-preview`), а также цели (`wasm32-unknown-unknown`).
- **Edition 2024.**
- **MSRV** задаётся в `workspace.package.rust-version` и проверяется в CI (`cargo-msrv` или job с этой версией). Политика: MSRV не новее, чем «stable минус N версий»; повышение MSRV — отдельное изменение в changelog (для libs — minor-релиз).
- `Cargo.lock` **коммитится** (в workspace есть бинари и оболочки).
- Dev-линковщик: `mold` (Linux) или `lld` — ускоряет итерации; не влияет на релиз.

### 2.2. Обязательные инструменты разработчика

| Инструмент | Зачем |
|---|---|
| `cargo fmt`, `cargo clippy` | формат и lints |
| `cargo-nextest` | быстрый, изолированный запуск тестов |
| `cargo-insta` | snapshot-тесты |
| `cargo-deny` | лицензии, дубли зависимостей, запрещённые крейты, advisories |
| `cargo-audit` или `cargo-vet` | уязвимости / аудит зависимостей |
| `cargo-semver-checks` | защита публичного API от случайных breaking changes |
| `cargo-llvm-cov` | покрытие |
| `cargo-fuzz` | фаззинг |
| `cargo-mutants` | мутационное тестирование |
| `cargo-hack` | проверка комбинаций feature-флагов |
| `cargo-machete` / `cargo-udeps` | неиспользуемые зависимости |
| `cargo-bloat`, `twiggy` | что раздувает бинарь / WASM |
| `hyperfine` | замер холодного старта CLI |
| `samply` / `cargo-flamegraph` / `perf` | профилирование CPU |
| `dhat` / `heaptrack` | профилирование аллокаций |
| `typos` | опечатки в коде и документации |

### 2.3. Единая конфигурация workspace

Все крейты наследуют версии, метаданные и lints из корневого `Cargo.toml` (`workspace.package`, `workspace.dependencies`, `workspace.lints`). Это исключает дрейф версий и разных настроек. Крейты, которым нужен `unsafe` (`wl-ffi`, `wl-py`, `wl-wasm`), **не наследуют** запрет и объявляют собственные lints с обязательным обоснованием (раздел 5). Готовые шаблоны — в [приложении A](#a-корневой-cargotoml).

### 2.4. Профили сборки

Одна настройка `panic` действует на весь профиль, поэтому нужны **отдельные профили**:

| Профиль | Назначение | Ключевые параметры |
|---|---|---|
| `release` | библиотека, FFI, PyO3 (нужен unwind для `catch_unwind`) | `lto="fat"`, `codegen-units=1`, `opt-level=3`, `strip="symbols"`, panic=unwind |
| `release-cli` | бинарь CLI | наследует `release`, `panic="abort"` (меньше бинарь, быстрее) |
| `release-wasm` | WASM | наследует `release`, `opt-level="z"` (или `"s"`), `panic="abort"` |
| `bench` | бенчмарки | наследует `release`, `debug=true` (для профилирования) |

Следствие: **FFI/PyO3 нельзя собирать с `panic="abort"`**, иначе перехват паник на границе не сработает и процесс-хозяин упадёт.

Дополнительные ускорители (проверять замером, не включать вслепую): **PGO** (`cargo-pgo`) и **BOLT** для CLI на репрезентативном корпусе виджетов; `mimalloc` как аллокатор CLI (не для WASM).

## 3. Стиль кода и дизайн API

### 3.1. Форматирование и lints

- `rustfmt` с конфигом из репозитория; запрет форматирования вручную. В CI: `cargo fmt --check`.
- `clippy` в CI с `-D warnings`.
- Набор lints (см. приложение A): `clippy::pedantic` как предупреждения с точечными разрешениями; для библиотечных крейтов — **запрет** `unwrap_used`, `expect_used`, `panic`, `indexing_slicing`, `todo`, `unimplemented`, `dbg_macro`, `print_stdout`, `print_stderr`; предупреждения `cast_possible_truncation` и `cast_sign_loss` (важно из-за `u32`-смещений); `missing_docs` для публичного API.
- `unwrap`/`expect` допустимы **только** в тестах, бенчмарках и `build.rs`, и в `main` бинарей — с осмысленным сообщением.

### 3.2. Стандарты именования и структуры

- Следовать **Rust API Guidelines**: именование (`as_`, `to_`, `into_`), реализация стандартных трейтов (`Debug`, `Clone`, `PartialEq`, `Eq`, `Hash`, `Default`, `Display` там, где уместно), `From`/`TryFrom` для преобразований.
- Модули по предметной области (`html`, `css`, `js`, `size`, `report`), а не по типам (`enums.rs`, `utils.rs` — запрещены: «свалки»).
- Файл ≤ ~500 строк как ориентир; функция — одна ответственность, цикломатическая сложность ограничивается `clippy::cognitive_complexity` (порог в конфиге).
- Один публичный тип — одно понятное назначение; приватные детали не торчат наружу.

### 3.3. Типы-обёртки (newtypes) и инварианты

```rust
#[derive(Clone, Copy, PartialEq, Eq, Hash, PartialOrd, Ord)]
pub struct RuleId(u16);                      // не String и не &str

#[derive(Clone, Copy, PartialEq, Eq, Debug)]
pub struct Span { pub start: u32, pub end: u32 }   // байтовые смещения, не line/col

#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug)]
pub enum Severity { Info, Warn, Error }

#[derive(Clone, Copy, PartialEq, Eq, PartialOrd, Ord, Debug)]
pub enum Confidence { Heuristic, Likely, Certain }
```

- Смещения хранить как `u32` (вход ≤ 1 МБ по потолку) — вдвое меньше памяти, чем `usize`; **конвертации — через проверенные функции** (`u32::try_from`), а не `as`.
- Строки и столбцы вычисляются **при формировании отчёта** по таблице начал строк (бинарный поиск), а не при каждом правиле.
- Конструкторы, проверяющие инварианты (`Span::new(start, end)` отклоняет `start > end`), вместо открытых полей там, где это важно.

### 3.4. Стабильность публичного API

- `#[non_exhaustive]` на публичных `enum` и `struct`, которые будут расти (`Severity`, `Report`, `Config`, виды диагностик).
- Конфигурация — через **builder** или `Default` + изменение полей в закрытой структуре; не десятки позиционных параметров.
- Закрытые (sealed) трейты там, где расширение извне не планируется.
- `cargo-semver-checks` в CI блокирует случайные breaking changes. Всё нестабильное — за feature-флагом `unstable`.
- JSON-контракт (`schema_version`) — такая же публичная поверхность, как и Rust API: изменение — только добавляющее внутри мажорной версии.

### 3.5. Документация в коде

- `#![warn(missing_docs)]` в библиотеках; у публичных функций — раздел `# Errors`, там, где возможны ошибки, и `# Examples` (они же doc-тесты).
- Комментарии объясняют **почему**, а не **что**. Каждая нетривиальная эвристика ссылается на раздел спецификации или ADR.

## 4. Обработка ошибок и политика паник

### 4.1. Разделение понятий

| Понятие | Что это | Как выражается |
|---|---|---|
| **Находка** (diagnostic) | Результат линтинга: виджет нарушает правило | элемент `Report.diagnostics`, не ошибка |
| **Ошибка использования** | Неверный конфиг, неподдерживаемый профиль, файл не найден | `Result<_, UsageError>` |
| **Ошибка ввода** | Невалидный UTF-8, превышен потолок размера | диагностика (`TGW004`) или `Err(InputError)` — по контракту, один раз и везде одинаково |
| **Внутренняя ошибка** | Баг ядра | `Err(InternalError)` с контекстом, **никогда** паника наружу |

### 4.2. Реализация

- В библиотеках — `thiserror` (типизированные ошибки). В бинарях — `miette` (красивые отчёты) или `anyhow`.
- Ядро возвращает `Result`; нигде нет `unwrap` на данных пользователя. Для индексирования — `get()`, `split_at_checked`, итераторы; не `slice[i]`.
- Арифметика на пользовательских размерах — `checked_*`/`saturating_*`; в release включены `overflow-checks = true` для ядра (цена мала, выигрыш — отсутствие тихих переполнений).
- Рекурсия по недоверенному вводу (вложенные теги, скобки) — **с ограничением глубины**, либо итеративно с явным стеком. Переполнение стека — это падение процесса.

### 4.3. Границы паник

- **FFI, PyO3, WASM-вход, LSP-обработчики** оборачиваются в `catch_unwind`. Паника превращается в структурированную внутреннюю ошибку (`{"error":{"kind":"internal",...}}`), процесс не падает.
- Для паник в CLI — установить `panic hook`, который печатает понятное сообщение, версию, и просит приложить входной файл в issue.
- Любая обнаруженная паника — **безусловный баг**: добавляется регрессионная фикстура и фаззинг-корпус.

## 5. Политика `unsafe`

1. `#![forbid(unsafe_code)]` во **всех** крейтах, кроме `wl-ffi`, `wl-py`, `wl-wasm` (там необходимые границы).
2. Каждый блок `unsafe` сопровождается комментарием `// SAFETY:` с доказательством инвариантов.
3. Минимальная площадь: `unsafe`-код живёт в маленьком модуле, обёрнутом безопасным API.
4. `cargo-geiger` или аналогичный отчёт о количестве `unsafe` в зависимостях — в CI как информационный артефакт; новая зависимость с большим объёмом `unsafe` требует обоснования.
5. Крейты с `unsafe` проходят `miri` (где применимо) и фаззинг входных точек.
6. Запрещено ради производительности «оптимизировать» безопасный код `unsafe`-ом без бенчмарка, доказывающего выигрыш, и без согласования в ADR.

## 6. Паттерны архитектуры ядра

### 6.1. Один проход по дереву, правила подписываются на типы узлов

Вместо «каждое правило — свой обход дерева» используется **единый обход** с диспетчеризацией событий:

```text
parse → Tree
  walk(Tree) ──► для каждого узла: visitors[node_kind] → rule.visit(node, &mut Cx)
```

- Правило объявляет, какие виды узлов его интересуют (битовая маска или таблица по `NodeKind`). Диспетчер вызывает только заинтересованные правила.
- Преимущества: один обход вместо десятков, предсказуемое поведение, лёгкое добавление правил. Ограничение: для входа ≤ 32 КБ выигрыш скромный — главная ценность в простоте и единообразии, а не в «ускорении». Не усложнять, если замер не показывает пользы.

### 6.2. Данные правил компилируются в код при сборке

- `ruleset/profile-1.toml` разбирается **в `build.rs`**, а множества («запрещённые элементы», «запрещённые API») генерируются как статические структуры (`phf`/отсортированные срезы/`match`). В рантайме — **нулевая стоимость разбора**, нулевая инициализация.
- Загрузка внешнего профиля из файла — отдельный feature-флаг для экспериментов и тестов; в продуктовой сборке не используется.
- Все метаданные правил (`RuleMeta`) — `static`; генерация страниц документации и `widgetlint explain` читают те же данные.

### 6.3. Контекст проверки

```rust
pub struct Cx<'a> {
    src: &'a Source,          // исходный текст + таблица строк (лениво)
    cfg: &'a Config,
    out: &'a mut Diagnostics, // накопитель находок
}
impl Cx<'_> {
    pub fn emit(&mut self, meta: &'static RuleMeta, span: Span, args: MsgArgs);
}
```

- `emit` проверяет конфиг (включено ли правило, переопределён ли уровень), подавления и пороги **до** формирования сообщения. Текст сообщения строится **лениво**, только если диагностика реально попадёт в отчёт.
- Сообщения — `&'static str` шаблоны + небольшие аргументы (`Cow`/срезы), а не `format!` в горячем пути.

### 6.4. Явный пайплайн вместо скрытого состояния

Стадии (`validate → parse → analyze → cross-checks → size → collect`) — отдельные функции с явными входами и выходами. Никаких `lazy_static` с изменяемым состоянием, синглтонов, thread-local кэшей, влияющих на результат.

### 6.5. Границы между крейтами

- `wl-core` зависит от анализаторов, но **не** от CLI/FFI/сети.
- Оболочки (`wl-cli`, `wl-wasm`, `wl-py`, `wl-ffi`, `wl-lsp`) — **тонкие**: преобразование аргументов, вызов ядра, форматирование вывода. Бизнес-логики в них нет, иначе нарушится паритет оболочек.
- Правило зависимостей проверяется в CI (раздел 14): ядро не может подтянуть сетевые крейты.

## 7. Производительность: методология

### 7.1. Где реально уходит время (гипотеза для проверки)

Вход ≤ 32 КБ. Ожидаемое распределение: парсинг HTML/CSS/JS — основная доля; zlib-9 (пять-шесть прогонов для разбивки) — вторая; сами правила — малая; **для CLI доминирует холодный старт процесса**, для WASM — загрузка и инициализация модуля. Эту гипотезу нужно проверить профилировщиком на M0, до любых оптимизаций.

### 7.2. Бюджеты (цели)

| Операция | Цель | Источник требования |
|---|---|---|
| `check` ядро на 32 КБ | ≤ 10 мс (p50) | внутренняя цель, строже NFR |
| `check` CLI end-to-end | ≤ 50 мс | NFR из спецификации |
| `size` | ≤ 10 мс | NFR из спецификации |
| WASM холодный старт | ≤ 300 мс | NFR из спецификации |
| Пиковая память на 32 КБ | цель — единицы МБ (измерить `dhat`) | внутренняя цель |
| Холодный старт CLI (`--version`) | измерить `hyperfine`, зафиксировать как базу | регрессии ловить в CI |

Бюджеты — **гейты**: регрессия больше порога блокирует слияние (раздел 13).

### 7.3. Инструменты и их роли

| Что измеряем | Инструмент | Заметка |
|---|---|---|
| Время функций (микробенчмарки) | `criterion` или `divan` | шумно на облачных CI; использовать локально и для трендов |
| **Число инструкций** (стабильно в CI) | `iai-callgrind` (требует Valgrind) | детерминирован — подходит для **жёстких гейтов** в CI |
| Холодный старт CLI | `hyperfine` | `--warmup`, сравнение до/после |
| CPU-профиль | `samply` / `flamegraph` / `perf` | сборка с `debug=true` в профиле `bench` |
| Аллокации | `dhat` / `heaptrack` | число и объём; цель — минимизировать число |
| Размер бинаря | `cargo-bloat`, `twiggy` (WASM) | в CI — отслеживание размера |

### 7.4. Процесс оптимизации (обязательный)

1. **Зафиксировать базу** — бенчмарк на репрезентативном корпусе (малые, средние, предельные виджеты; «патологические» случаи — глубокая вложенность, много правил, длинные строки).
2. **Профиль до изменения** — найти реальное горлышко.
3. **Одно изменение — одно измерение.**
4. **Проверить корректность** — golden/snapshot-тесты зелёные, вывод не изменился ни на байт.
5. **Записать результат** в PR: до/после, метод, железо.
6. Если выигрыш в пределах шума — **не вносить усложнение**.

### 7.5. Корпус для бенчмарков

- Каталог `bench-corpus/`: минимальный виджет; «Order #1042» из документации; виджеты у границы 4 КБ; виджет на 32 КБ; синтетические патологические случаи (глубокие вложения, сотни CSS-правил, длинные строки, много обработчиков).
- Корпус фиксирован и версионируется; изменения — отдельным PR, чтобы сравнения оставались честными.

## 8. Производительность: конкретные приёмы

Приёмы ниже применяются **только после** подтверждения замером; они перечислены как арсенал, а не как обязательный минимум.

### 8.1. Запуск и инициализация

- **Нулевая инициализация в рантайме.** Статические множества профиля — на этапе сборки (раздел 6.2). Регулярные выражения не компилируются на горячем пути: заранее собранные автоматы в `OnceLock`/на этапе сборки, либо вовсе без регулярок.
- Для CLI: выбрать лёгкий разбор аргументов, если `clap` заметно влияет на холодный старт (замерить `hyperfine`); избегать тяжёлой инициализации логирования по умолчанию.
- `tracing` — за feature-флагом и только в бинарях; в ядре — компилируется «в ноль».

### 8.2. Поиск и сопоставление

- Множества имён (элементы, свойства, API): для небольших фиксированных наборов достаточно `match` по `&str` или отсортированного среза с `binary_search`; для крупных — `phf` (на этапе сборки). **Не** `HashSet<String>`, собираемый в рантайме.
- Регистронезависимое сравнение — `eq_ignore_ascii_case` без аллокаций; HTML-имена и CSS-ключевые слова — ASCII.
- Поиск подстрок и байтов — `memchr`/`memchr::memmem`; множественный поиск паттернов (секреты, списки API в тексте) — `aho-corasick` как предфильтр, регулярка — только на кандидатах.
- Энтропийная проверка секретов — только для строк-кандидатов длиннее порога, не для каждой строки.

### 8.3. Парсинг

- **Разбор каждого языка один раз.** Деревья переиспользуются всеми правилами; никаких повторных разборов «для удобства» правила.
- Для JS (`oxc`) — парсер использует арену аллокаций (по дизайну); держать её на время вызова и сбрасывать целиком.
- Для CSS — не строить лишних промежуточных структур; считать правила и `@keyframes` в том же проходе, что и проверку свойств.
- Пропускать работу: если на входе нет `<script>`, JS-стадия не запускается; нет `<style>` и `style=""` — пропускается CSS.

### 8.4. Анализ потока JS (самое дорогое)

- Резюме функций (summaries): для каждой локальной функции один раз вычисляется «какие привилегированные вызовы достижимы синхронно» и кэшируется; обход графа вызовов — O(n·d) с ограничением глубины.
- Ранний выход: если в коде нет ни одного привилегированного вызова (проверка предфильтром по тексту), анализ тап-синхронности не запускается.
- Не строить полный граф потока управления там, где достаточно синтаксических признаков (`await`, `.then`, таймеры).

### 8.5. Размер (zlib)

- Использовать один экземпляр компрессора и `reset()` между прогонами (в `flate2` — `Compress::reset`), заранее выделить выходной буфер на `compress_bound`; не создавать компрессор на каждый вызов.
- Разбивка требует N+1 прогонов (N — число частей, порядка 5): при 32 КБ это миллисекунды; **не распараллеливать** — накладные расходы потоков больше выигрыша. Если замер покажет иное — решать по данным.
- Результат сжатия кэшируется в рамках одного вызова: `C(целое)` вычисляется один раз и используется всеми правилами и разбивкой.

### 8.6. Вывод

- Сериализовать JSON напрямую в буферизованный writer (`serde_json::to_writer` в `BufWriter`), а не через промежуточную `String`.
- Для WASM — сравнить два способа передачи отчёта в JS: строка JSON + `JSON.parse` против прямой сериализации объектов (`serde-wasm-bindgen`); выбрать победителя **замером**, обычно строка быстрее на крупных структурах.
- Цветной вывод и красивые отчёты — только для TTY; в режиме CI/pipe — минимальный вывод.

### 8.7. Режим каталога (много файлов)

- Параллелизм **между файлами** (`rayon`), не внутри одного файла: файл мал, потоки не окупаются.
- Обход файловой системы — крейт `ignore` (учёт `.gitignore`, быстрый параллельный обход).
- Результаты собираются **в детерминированном порядке** (сортировка по пути) независимо от порядка завершения потоков.
- Ограничить число потоков конфигом (`--jobs`); по умолчанию — число логических ядер.

### 8.8. Чего не делать ради скорости

- Не писать собственный парсер HTML/CSS/JS без крайней необходимости: корректность хуже, поддержка дороже, выигрыш мал на 32 КБ.
- Не заменять безопасный код `unsafe` без бенчмарка и ADR.
- Не внедрять «умные» кэши между вызовами в ядре: это нарушает чистоту и детерминированность.
- Не оптимизировать то, чего нет в профиле CPU.

## 9. Память и аллокации

- **Арена на вызов.** Дерево AST и временные структуры живут в арене (`bumpalo` или арена парсера), которая освобождается разом по завершении вызова. Нет `Rc`/`Arc` в ядре без обоснования.
- **Нет клонирования деревьев.** Передавать ссылки; если нужна независимая копия — это сигнал пересмотреть дизайн.
- **Сокращать мелкие аллокации:** `SmallVec` для коротких списков (атрибуты, аргументы), `Cow<'static, str>` для сообщений, повторное использование буферов (`Vec::clear` вместо новой аллокации) внутри вызова.
- **Интернирование строк** (имён классов/идентификаторов) — только если замер покажет много дубликатов; для `pack` с сокращением имён — обязательно, там это часть алгоритма.
- **Ограничения ресурсов:** потолок размера входа (по умолчанию 1 МБ), предел глубины вложенности, предел числа диагностик (защита от «взрыва» отчёта на враждебном вводе), предел длины одной строки для регулярок.
- **Профилирование аллокаций** (`dhat`) на корпусе: число аллокаций на средний виджет — метрика, за которой следим по тренду.
- Для CLI: `mimalloc` — вариант, если замер даёт выигрыш; для WASM — аллокатор по умолчанию (меньше размер), либо `talc`/`lol_alloc` только после замера размера.

## 10. Детерминированность и параллелизм

### 10.1. Правила детерминированности

- **Нельзя полагаться на порядок итерации `HashMap`/`HashSet`** при формировании вывода. Для упорядоченных данных — `BTreeMap`/`IndexMap`, либо сортировка перед выводом.
- Диагностики сортируются **стабильно** по ключу `(span.start, rule_id, span.end)`; при равенстве — по порядку эмиссии.
- Никаких `SystemTime`, `Instant` в данных вывода; никаких случайных идентификаторов; никаких путей, зависящих от среды (`\\` против `/`) — пути нормализуются.
- Числа с плавающей точкой в отчёте — избегать; если нужны (проценты разбивки) — форматировать фиксированной точностью и **одинаково** во всех оболочках.
- Локаль не влияет на вывод; сообщения — на одном языке на релиз (локализация — отдельный слой, вне ядра).

### 10.2. Проверка

- В CI каждый golden-тест запускается **дважды** в разных условиях (разный порядок потоков, разный `HASH`-seed) — вывод обязан совпасть.
- Паритет оболочек (CLI = WASM = Python = C ABI) — отдельный гейт (раздел 12.6).

### 10.3. Потокобезопасность

- Ядро **без состояния**: `lint` — чистая функция, безопасна для вызова из многих потоков одновременно. Типы `Config`, `Report` — `Send + Sync`.
- Глобальных изменяемых данных нет; единственные допустимые глобальные — неизменяемые `static` (множества профиля) и `OnceLock` для неизменяемой инициализации.

## 11. Размер бинарников: CLI и WASM

### 11.1. WASM

- Профиль `release-wasm`: `opt-level="z"`, `lto`, `codegen-units=1`, `panic="abort"`, `strip`.
- После сборки — `wasm-opt -Oz` (binaryen); анализ состава — `twiggy top`/`twiggy dominators`.
- Урезать зависимости: `default-features = false` для `lightningcss`, `html5ever`, `oxc` и др., отключать Unicode-таблицы и ненужные форматы; вместо полноценного `regex` — `regex-lite`/`aho-corasick`/ручные автоматы; не использовать `format!`/`std::fmt` в горячих и частых путях без необходимости (раздувают код).
- Без потоков, без `std::fs`, без `SystemTime` (в `wasm32-unknown-unknown` они недоступны или бесполезны).
- **Гейт размера в CI:** размер `.wasm` (до и после gzip/brotli) сравнивается с базой; рост больше порога блокирует слияние без явного обоснования.
- Загрузка в песочнице — **потоковая** (`WebAssembly.instantiateStreaming`), выполнение вне UI-потока (Web Worker), чтобы не блокировать интерфейс.

### 11.2. CLI

- Профиль `release-cli`: `lto="fat"`, `codegen-units=1`, `panic="abort"`, `strip`. Статическая линковка (musl) для Linux-дистрибутива, по возможности.
- Отслеживать размер и время холодного старта как метрики качества.
- Опционально PGO/BOLT — только при подтверждённом выигрыше на корпусе.

## 12. Тестирование

### 12.1. Пирамида

| Уровень | Цель | Инструмент | Кто запускает |
|---|---|---|---|
| Юнит | отдельные функции и правила | `cargo nextest` | каждый PR |
| Snapshot / golden | стабильность вывода диагностик и отчёта | `insta` | каждый PR |
| Doc-тесты | примеры в документации работают | `cargo test --doc` | каждый PR |
| Property-based | инварианты на случайных данных | `proptest` | каждый PR (малый бюджет), ночью (большой) |
| Фаззинг | отсутствие паник и зависаний на враждебном вводе | `cargo-fuzz` | ночью + короткий smoke в PR |
| Паритет оболочек | CLI == WASM == Python == C ABI | матрица CI | каждый PR |
| Паритет zlib | Rust-счётчик == Python-счётчик | скрипт + CI | каждый PR |
| Производительность | регрессии по инструкциям и размеру | `iai-callgrind`, гейт размера | каждый PR |
| Мутационные тесты | качество тестов правил | `cargo-mutants` | еженедельно |
| Покрытие | пробелы в тестах | `cargo-llvm-cov` | каждый PR (тренд), порог на ядро |
| Калибровка | соответствие реальным клиентам | зонд-виджет | вручную по расписанию |

### 12.2. Тесты правил: обязательные требования

- Для каждого правила — **минимум две фикстуры**: «срабатывает» и «не срабатывает» (граничный случай). Гейт в CI: правило без обеих фикстур не проходит.
- Фикстура = исходник + ожидаемый JSON (`insta`-снимок). Изменение снимка — осознанное решение с ревью (`cargo insta review`).
- Тесты называются по ID правила и сценарию (`tgw100_removes_input_with_content`), чтобы падение сразу указывало на предмет.
- Для правил с эвристикой — фикстуры **ложных срабатываний**, которые зафиксированы как «не должно срабатывать».

### 12.3. Property-based инварианты

1. `lint` не паникует ни на каком входе (произвольные байты, включая невалидный UTF-8, NUL, огромные строки).
2. `lint(x)` детерминирован: два вызова дают равный `Report`.
3. Порядок диагностик стабилен и отсортирован.
4. `pack(pack(x)) == pack(x)` (идемпотентность).
5. `lint(pack(x))` не содержит новых находок относительно `lint(x)` (монотонность).
6. `size(pack(x)).zlib9 ≤ size(x).zlib9`.
7. Подавления (`tgw-disable`) убирают ровно заявленные находки и ничего больше.
8. Любой `Span` лежит в границах входа и на границах символов UTF-8.

Файлы регрессий `proptest` **коммитятся**.

### 12.4. Фаззинг

- Цели: разбор HTML (фрагменты), разбор CSS, разбор JS, загрузчик профиля, конфиг, входные точки FFI/WASM/Python.
- Корпус: минимальный набор в репозитории (малые файлы), расширенный — артефактом CI. Найденные падения → фикстура → исправление → регрессионный тест.
- Санитайзеры (`-Zsanitizer=address`) для крейтов с `unsafe`.
- Ограничения на время и память в фаззинг-целях, чтобы ловить зависания (алгоритмическая сложность), а не только паники.

### 12.5. Мутационное тестирование и покрытие

- `cargo-mutants` на анализаторах правил показывает, замечают ли тесты изменение логики; цель — высокий процент «убитых» мутантов на правилах (порог определить на первом прогоне; ориентир — не ниже 80%).
- Покрытие строк ядра — порог (ориентир ≥ 85%); покрытие — индикатор пробелов, а **не самоцель**: покрытие без проверок бессмысленно, поэтому оно дополняется мутационным анализом.

### 12.6. Паритет оболочек

Корпус фикстур прогоняется через CLI, WASM (Node), Python-колесо и C ABI; JSON сравнивается **побайтово**. Расхождение блокирует слияние. Единственное допустимое исключение — явное поле `approximate` в размере для WASM, если точный zlib недоступен.

### 12.7. Паритет zlib

Скрипт сравнивает счётчик Rust с `zlib.compress(data, 9)` Python на корпусе ≥ 500 файлов (пустой, 1 байт, границы 4096/32768, случайные данные, повторяющиеся блоки). Скрипт **печатает реализацию zlib** и отказывается работать на zlib-ng.

### 12.8. Организация тестов

- Юнит-тесты — рядом с кодом (`#[cfg(test)]`); интеграционные — в `tests/` крейта; общий корпус — в `fixtures/`.
- Никаких тестов, зависящих от сети, часов, порядка выполнения или состояния файловой системы вне временных каталогов.
- Каждый тест независим и быстрый; медленные — помечены и вынесены в отдельный профиль `nextest`.

## 13. CI/CD и релизы

### 13.1. Проверки на каждый PR (блокирующие)

1. `cargo fmt --check`
2. `cargo clippy --workspace --all-targets --all-features -- -D warnings`
3. `cargo nextest run --workspace` (+ `cargo test --doc`)
4. `cargo hack check --feature-powerset` (для крейтов с feature-флагами; в ограниченном виде, чтобы не взрывать время)
5. `cargo doc --no-deps` с `RUSTDOCFLAGS="-D warnings"`
6. `cargo deny check` (лицензии, advisories, bans, sources)
7. `cargo-semver-checks` для публичных крейтов
8. `typos`
9. Проверка MSRV
10. Паритет оболочек и паритет zlib
11. Гейт числа инструкций (`iai-callgrind`) и гейт размера WASM
12. Проверка покрытия правил фикстурами
13. Проверка «ядро без сети»: ядро не тянет сетевых зависимостей
14. Короткий фаззинг-smoke (по минуте на цель)

### 13.2. Ночные и еженедельные задания

- Длинный фаззинг, мутационное тестирование, `spec-watch`, расширенный proptest, полная матрица feature-флагов, профили производительности как артефакты.

### 13.3. Матрица

Linux/macOS/Windows × stable + MSRV (для ядра); отдельные задания: сборка и тест WASM в Node, колёса Python (manylinux/macOS/Windows, abi3), C ABI (проверка заголовка и сборка примеров на C), LSP smoke.

### 13.4. Скорость CI

- Кэш зависимостей и сборки (`Swatinem/rust-cache`, при необходимости `sccache`).
- `nextest` с разбиением на партии; тяжёлые задания — параллельно; быстрые проверки (fmt, clippy) — первыми, чтобы падать рано.
- Бенчмарки по времени — **не гейты** на шумных раннерах; гейты — по числу инструкций (детерминировано).

### 13.5. Релизы

- **Семантическое версионирование** и **Conventional Commits** (`feat:`, `fix:`, `perf:`, `refactor:`, `docs:`, `test:`, `chore:`, `BREAKING CHANGE:`); changelog генерируется автоматически (`release-plz` или `cargo-release`).
- Один тег — одна версия во всех пакетах (crates.io, npm, PyPI, бинарники).
- Бинарные релизы CLI — `cargo-dist` (установщики, архивы, контрольные суммы).
- Колёса Python — `maturin` (GitHub Action), **trusted publishing** по OIDC без долгоживущих токенов.
- npm — публикация с провенансом (`--provenance`).
- crates.io — trusted publishing, где доступно.
- Артефакты релиза сопровождаются **аттестациями происхождения сборки** (`actions/attest-build-provenance`) и SBOM.
- Changelog содержит отдельный раздел «изменения набора правил»: добавлено / изменён уровень / устарело.

### 13.6. Политика ветвления

- `main` защищён: слияние только через PR с зелёным CI и минимум одним ревью.
- Короткоживущие ветки; squash-merge с заголовком в формате Conventional Commits.
- Релизные ветки — только для патчей к предыдущим мажорным версиям.

## 14. Безопасность и цепочка поставок

### 14.1. Зависимости

- **Политика минимума:** каждая новая зависимость в `wl-core` оформляется кратким обоснованием в PR: что даёт, размер, влияние на время сборки, сопровождение, объём `unsafe`, лицензия. Список разрешённых зависимостей ядра — явный (allowlist).
- `cargo-deny`: разрешённые лицензии (MIT, Apache-2.0, BSD, ISC, Unicode и т.п. — список в `deny.toml`), запрет неподдерживаемых/уязвимых крейтов, предупреждение о дублирующихся версиях, разрешённые источники (только crates.io и явно перечисленные репозитории).
- `cargo-audit` или `cargo-vet` — в CI; уязвимость высокой серьёзности блокирует слияние.
- Регулярные автоматические обновления зависимостей (Dependabot/Renovate) с обязательным прохождением всех гейтов.
- `Cargo.lock` коммитится; сборки релиза — с `--locked`.

### 14.2. Изоляция ядра от сети

- В `deny.toml` — запрет сетевых крейтов для `wl-core` (через `bans` и проверку дерева зависимостей, например `cargo tree -p wl-core` + скрипт-проверка в CI). Единственный крейт с сетью — `wl-spec-watch`.

### 14.3. GitHub Actions

- Действия фиксируются **по SHA коммита**, не по тегам; обновляются ботом.
- Минимальные права токена (`permissions:` на уровне задания, по умолчанию read-only).
- Секреты не доступны PR из форков; публикация — только из защищённых окружений и по OIDC.
- Отдельная защита окружения `release` (ревьюеры, ограничение веток).

### 14.4. Безопасность обработки ввода

- Все лимиты ресурсов (раздел 9) включены по умолчанию.
- Защита от «взрыва» сложности: ограничения глубины, длины, числа узлов, числа диагностик; фаззинг на тайм-аут.
- WASM-сборка работает в песочнице окружения; CLI не исполняет содержимое виджета, **только анализирует** (симулятор, когда появится, выполняет JS в изолированном QuickJS с жёсткими лимитами CPU и памяти — это отдельный раздел безопасности в его дизайне).
- Политика раскрытия уязвимостей: `SECURITY.md`, приватный канал сообщений.

### 14.5. Воспроизводимость

- Закреплённый тулчейн, `--locked`, детерминированные сборки по возможности; контрольные суммы артефактов в релизе.

## 15. Руководство по оболочкам: WASM, Python, C ABI

### 15.1. Общие правила

- Оболочка **не содержит логики линтинга**: принимает вход, вызывает `wl-core`, возвращает JSON/структуры и ошибки в едином формате.
- Все ошибки — в общем формате `{"error":{"kind":"usage|input|internal","message":"..."}}`; паники перехватываются.
- Единая версия ядра и оболочек; метод `version()` возвращает версию ядра и версию профиля.

### 15.2. WASM / npm

- `wasm-bindgen` + `wasm-pack`/`wasm-bindgen-cli`; публикация двух вариантов: `bundler` и `nodejs`/`web` (ESM).
- Типы TypeScript (`.d.ts`) генерируются из Rust-типов (`tsify`/`specta` или собственная схема) и **проверяются в CI** на соответствие JSON-схеме отчёта.
- API чистое и без состояния: `lint`, `size`, `pack`, `version`. Никаких глобальных инициализаций, кроме загрузки модуля.
- `console_error_panic_hook` — только в отладочной сборке.
- Не использовать API, недоступные в `wasm32-unknown-unknown` (потоки, файловая система, часы).

### 15.3. Python / PyPI

- `PyO3` + `maturin`, **abi3-колёса** (один бинарь на несколько версий Python), поддержка актуальных Python 3.x.
- Поставлять **типы**: `.pyi`-заглушки и `py.typed`; тип результата — `TypedDict`/`dataclass` по схеме отчёта.
- На время работы ядра **освобождать GIL** (`allow_threads`/`detach` — название зависит от версии PyO3), так как ядро — чистое и не трогает объекты Python.
- Возврат результата: сравнить замером «JSON-строка + `json.loads`» и прямое построение объектов; выбрать быстрее.
- Исключения Python — для ошибок использования и внутренних; **находки не исключения**.

### 15.4. C ABI

- Заголовок генерируется `cbindgen` и проверяется в CI (изменение заголовка — осознанное, с обновлением ABI-версии).
- Контракт: вход — указатели на UTF-8 строки (`const char*`, с нулевым терминатором) или пара `(ptr, len)`; выход — `char*` с JSON, который **освобождает вызывающий** через `wl_free`.
- Функция `wl_abi_version()` — для проверки совместимости при динамической загрузке.
- Все `extern "C"` функции — в `catch_unwind`; ни одна паника не пересекает границу.
- Нет глобального состояния → потокобезопасно по построению; это документируется.
- Примеры на C и Go в CI собираются и запускаются на фикстурах.

### 15.5. LSP

- На базе `tower-lsp`; пересчёт диагностик при изменении документа с **debounce**; размер документа ограничен тем же потолком; ядро вызывается вне основного цикла событий.
- Диагностики LSP получаются из `Report` без повторной логики; уровни и коды соответствуют правилам; `code_description` ссылается на страницу правила.

### 15.6. Rust-библиотека и макрос

- `wl-core` публикуется как библиотека с минимальным набором зависимостей; `wl-macros` (`widget!`) использует ядро на этапе компиляции; ошибки — через `compile_error!` с точными позициями (`proc_macro::Span`/`proc-macro2` с `syn::Error`).

### 16.4. Процесс изменения

1. Issue или обсуждение для нетривиальных изменений (особенно новых правил).
2. PR маленький и сфокусированный; описание содержит «что и почему», ссылку на раздел спецификации, результаты бенчмарков для `perf:`-изменений.
3. Ревью по чек-листу (раздел 17).
4. Squash-merge, заголовок в формате Conventional Commits.

## 17. Чек-листы

### 17.1. Definition of Done — новое правило

- [ ] Присвоен стабильный `TGWxxx`, ID не использовался ранее.
- [ ] Метаданные заполнены: уровень, уверенность, фаза, ссылка на раздел спецификации, краткое описание, подсказка «как исправить».
- [ ] Данные профиля (если нужны) добавлены в TOML, а не зашиты в код.
- [ ] Минимум две фикстуры: срабатывает / не срабатывает; для эвристик — фикстуры ложных срабатываний.
- [ ] Snapshot-тесты зафиксированы и проверены глазами.
- [ ] Нет паник и неограниченной рекурсии на любых входах (proptest/фаззинг-цель покрывает).
- [ ] Бенчмарк не показывает регрессию сверх порога.
- [ ] Страница правила сгенерировалась и корректна.
- [ ] Запись в `CHANGELOG.md` (раздел о правилах).
- [ ] Паритет оболочек зелёный.

### 17.2. Definition of Done — релиз

- [ ] Все гейты CI зелёные на теге.
- [ ] `cargo-semver-checks` без breaking changes (или мажорная версия поднята).
- [ ] Changelog обновлён (код и правила).
- [ ] Бенчмарки, размер WASM и CLI сопоставлены с базой.
- [ ] Паритет оболочек, паритет zlib, калибровка (если менялся профиль).
- [ ] Артефакты подписаны/аттестованы, контрольные суммы опубликованы.
- [ ] Документация и песочница обновлены.

### 17.3. Чек-лист ревью кода

**Корректность**
- [ ] Нет `unwrap`/`expect`/индексации в путях пользовательских данных.
- [ ] Арифметика безопасна (`checked_*`, `u32::try_from`), нет молчаливых усечений.
- [ ] Рекурсия ограничена по глубине.
- [ ] Границы `Span` корректны, на границах символов UTF-8.

**Дизайн**
- [ ] Типы кодируют инварианты (нет «голых» строк/чисел там, где есть доменный тип).
- [ ] Публичный API минимален; `#[non_exhaustive]` где нужно.
- [ ] Оболочки не получили логику линтинга.
- [ ] Новые зависимости обоснованы.

**Детерминированность**
- [ ] Нет зависимости вывода от порядка `HashMap`, времени, потоков, платформы.

**Производительность**
- [ ] Для `perf:` — приложены замеры до/после.
- [ ] Нет повторных разборов, лишнего клонирования, аллокаций в горячем пути без причины.
- [ ] Нет неизмеренных «оптимизаций».

**Тесты и документация**
- [ ] Тесты проверяют поведение, а не реализацию; граничные случаи покрыты.
- [ ] Документация и changelog обновлены.

### 17.4. Чек-лист появления регрессии производительности

1. Воспроизвести на корпусе, зафиксировать числа (инструкции и время).
2. `git bisect` по тегам/коммитам с гейтом инструкций.
3. Профиль до/после (`samply`/`flamegraph`).
4. Исправить или откатить; добавить бенчмарк, который бы это поймал.
5. Запись в ADR или заметку о причине, если урок общий.

## 18. Антипаттерны

| Антипаттерн | Почему плохо | Что делать |
|---|---|---|
| Глобальное изменяемое состояние / кэши в ядре | Нарушает чистоту, детерминированность, потокобезопасность | Состояние — в `Cx` на время вызова |
| Компиляция регулярок в горячем пути | Дорого на каждый вызов | Предкомпилированные автоматы, `aho-corasick`, без регулярок там, где можно |
| Полный разбор «для удобства правила» повторно | Дорого и разъезжается с общим деревом | Один разбор, общие ссылки |
| `HashMap` в формировании вывода | Недетерминированный порядок | `BTreeMap`/сортировка |
| `unwrap` на пользовательских данных | Паника = уязвимость | `Result`, `get`, итераторы |
| `as` для сужающих преобразований | Тихое усечение | `try_from`, проверенные функции |
| Строковые идентификаторы правил | Опечатки, нет проверок компилятора | `RuleId`, сгенерированные константы |
| Логика в оболочках | Расхождение между языками | Только ядро, оболочки тонкие |
| Ранняя «оптимизация» без профиля | Усложнение без выигрыша | Методология раздела 7 |
| Параллелизм внутри одного маленького файла | Накладные расходы > выигрыша | Параллелизм между файлами |
| Бенчмарки по времени как жёсткий гейт на облачном CI | Шум, ложные срабатывания | Гейт по числу инструкций, время — тренд |
| Snapshot-тесты «принять всё» | Скрытые регрессии | Просмотр каждого изменения |
| Тесты, зависящие от сети/времени | Нестабильность | Изолированные, детерминированные |
| Ослабление правила, чтобы «убрать шум» | Потеря доверия к `certain` | Понизить уверенность или поправить фикстуры, а не ловить всё подряд |
| Зависимости «на всякий случай» | Размер, поверхность атаки, время сборки | Allowlist, обоснование в PR |
| Правки сгенерированных документов вручную | Расхождение с данными | Править данные/фикстуры |

### K. Порядок внедрения стандартов (минимально жизнеспособный)

Чтобы стандарты не затормозили старт, включать их по ступеням:

1. **День 1 (M0):** workspace, toolchain, `fmt`/`clippy`/`nextest`, `forbid(unsafe)`, политика паник, `cargo-deny`, коммит `Cargo.lock`.
2. **До релиза v0.1 (M1):** snapshot-тесты, гейт «две фикстуры на правило», паритет zlib, базовый корпус бенчмарков, `iai-callgrind`-гейт, фаззинг-smoke.
