## 1. Резюме

Bot API 10.4 (9 ноября 2026) добавила **виджеты**: интерактивные HTML/CSS/JS-блоки внутри сообщения. Виджет исполняется в песочнице QuickJS без сети, ограничен 32 КБ HTML и **4 КБ после сжатия zlib level 9**, а клиент молча вырезает всё, что не входит в *widget profile*. Ошибки такого рода не видны ни разработчику, ни серверу.

`widgetlint` — набор инструментов, который закрывает этот разрыв:

- **`check`** — статический линтер: что сервер откажет, что клиент молча вырежет, что нарушает правила поведения (жесты, тап-синхронность, состояние, кошелёк);
- **`size`** — точный подсчёт сжатого размера с разбивкой «куда ушли байты»;
- **`pack`** — оптимизатор, минимизирующий именно *сжатый* размер и не выводящий виджет за пределы профиля;
- **`sim`** — симулятор на QuickJS с моком `TelegramWidget` для проверки рантайм-лимитов (фаза 3);
- **`spec-watch`** — наблюдатель, который ловит изменения официальной спецификации.

Ядро — чистая функция без ввода-вывода на Rust. Оно раздаётся как CLI (JSON/SARIF), WASM (npm и онлайн-песочница), PyO3-колесо, C ABI, GitHub Action, pre-commit-хук и LSP. Это даёт инструменту аудиторию Python- и JS-разработчиков ботов, а не только Rust-сообщества. Поверх ядра — Rust-специфичный слой: макрос `widget!`, который не даёт скомпилироваться невалидному виджету, и типизированные состояния с контролем лимита 1024 байта.

## 2. Проблема и обоснование

### 2.1. Почему это болезненно

1. **Бюджет 4 КБ.** Сжатый размер определяется на сервере zlib level 9. Типичный разработчик упирается в лимит быстро и не понимает, какая часть кода «съела» байты. Ошибка приходит только как `INPUT_MEDIA_WIDGET_TOO_LARGE` — причём для HTML меньше 32 КБ это означает, что сработал именно сжатый лимит.
2. **Молчаливое вырезание.** Клиент проверяет каждое изменение страницы на соответствие профилю и рисует только прошедшее. Вырезанное — *не ошибка*: виджет продолжает работать, но выглядит или ведёт себя не так. В документации это прямо названо риском («out feature is a bug you will not see»).
3. **Неочевидные правила поведения.** Вызовы `request`, `openLink`, `copyText` допустимы только синхронно в обработчике тапа, один вызов на тап; вертикальные драги всегда принадлежат чату; горизонтальные драги и холды требуют явного `touch-action`; в первых 20 px нет жестов (системный «назад»). Нарушение даёт тихий отказ.
4. **Много окружений.** Приватный чат, группа, inline, форвард статического виджета, форвард общего виджета, превью — у каждого свои права (`viewer`, `request`, `chatData`). В production сейчас доступен только приватный чат, остальное — тестовый сервер.
5. **Свежесть.** Экосистема инструментов пуста: документации неделя, библиотек для виджетов практически нет.

### 2.2. Почему именно линтер

- Правила профиля **формализуемы**: в документации есть явные списки «In/Out», таблица лимитов и таблицы прав. Это почти готовая спецификация, а не размытая «лучшая практика».
- Линтер **полезен вне зависимости от языка бота** — в отличие от Rust-фреймворка, который нужен только Rust-разработчикам.
- Он **дешёвый в первой версии** (недели, а не месяцы), но имеет «длинный хвост» развития (pack, sim, LSP).
- Он естественно ложится на существующий стиль «conformance-гейтов».

## 3. Цели, не-цели, принципы

### 3.1. Цели

- **G1.** Точно предсказывать отказ сервера по размеру и формату (паритет с zlib Python на реальных файлах).
- **G2.** Находить всё, что клиент вырежет или проигнорирует по профилю 1.
- **G3.** Находить нарушения правил поведения с оценкой уверенности.
- **G4.** Давать одинаковый результат во всех оболочках (CLI, WASM, Python, C ABI) — байт-в-байт для JSON.
- **G5.** Держать правила как **данные**, версионируемые по номеру профиля, чтобы обновление спецификации не требовало переписывания кода.
- **G6.** Быть быстрым, детерминированным и безопасным на недоверенном вводе.

### 3.2. Не-цели

- **N1.** Не заменять клиент Telegram и не рендерить виджет пиксель-в-пиксель. Документация сама говорит, что браузер — не Telegram-клиент.
- **N2.** Не доказывать корректность произвольного JS. Анализ эвристический, там, где точности нет, диагностика помечается уровнем уверенности.
- **N3.** Не заниматься Mini Apps (отдельная технология). Возможные общие компоненты — в будущем, вне объёма v1.
- **N4.** Не быть Bot API-фреймворком. Интеграции — тонкие адаптеры.

### 3.3. Принципы

1. **Меньше ложных срабатываний лучше, чем больше находок.** Каждая диагностика несёт `confidence`; по умолчанию показываются `certain` и `likely`.
2. **Источник правды — документация, ссылка на раздел в каждом правиле.**
3. **Неполные списки — не повод для ошибок.** Списки «In» в документации оканчиваются на «…», поэтому неизвестное — это `info`, а не `warn`.
4. **Стабильные ID.** Идентификатор правила не переиспользуется никогда.
5. **Чистое ядро.** Никаких часов, сети, файловой системы, случайности в `wl-core`.

## 4. Контекст: что известно о виджетах

Ниже — сжатый свод фактов, на которых построены правила. Все значения взяты из документации Bot API 10.4 на 15.11.2026.

### 4.1. Природа виджета

- Один самодостаточный HTML-документ (допускается фрагмент без `<html>`/`<body>`), inline `<style>` и `<script>`, изображения только как `data:` URL или inline SVG.
- Код фиксируется при отправке и **никогда не меняется**; меняется только **состояние**, и пишет его только бот: `chat_data` (привязано к одному сообщению, в группе общее для всех участников, в форварде отсутствует) и `public_data` (общее состояние, виджет видит везде).
- Исполнение: QuickJS (интерпретатор, без JIT), никакого WebView. DOM-изменения проверяются клиентом по профилю.
- Сеть отсутствует: `fetch`, `XMLHttpRequest`, `WebSocket` и подобные бросают `NetworkDisabledError`. Внешние скрипты, стили, шрифты, изображения не загружаются.
- Единственный выход наружу — `TelegramWidget.request(data)` (1–64 байта), приходит боту как `widget_query` (или `shared_widget_query` из форварда общего виджета). Ответ бота — `answerWidgetQuery`, до 1024 байт, за 15 секунд.

### 4.2. Размеры и лимиты (источник для правил TGW0xx и TGW3xx)

| Лимит | Значение | Последствие |
|---|---|---|
| HTML | 32768 байт UTF-8 | `INPUT_MEDIA_WIDGET_TOO_LARGE` |
| Сжатый HTML | 4096 байт, zlib level 9 | `INPUT_MEDIA_WIDGET_TOO_LARGE` |
| Корректность HTML | валидный UTF-8, без NUL (U+0000) | `INPUT_MEDIA_WIDGET_HTML_INVALID` |
| `chat_data`, `public_data` | по 1024 байта UTF-8 каждое | `INPUT_MEDIA_WIDGET_DATA_TOO_LARGE`; в правках — `WIDGET_DATA_INVALID` и др. |
| `data` запроса | 1–64 байта | `TypeError` в виджете |
| `data` ответа | до 1024 байт | `WIDGET_RESULT_TOO_LARGE` |
| Время ответа бота | 15 секунд | `TIMEOUT` |
| Запросы на пользователя и бота | 5 за 5 секунд | `RATE_LIMITED` |
| Фоновые запросы | только приватный чат, один при появлении, затем не чаще 1 в 5 секунд | `NOT_ALLOWED` / `RATE_LIMITED` |
| Правки общего виджета | 1 в секунду; `cache_time` 5–3600 с | flood wait / `invalid cache time specified` |
| Пузырь | 200–600 px по ширине, 50–600 по высоте | содержимое обрезается |
| Web Storage | 4 КБ на область на сообщение | `QuotaExceededError` |
| `copyText` | 1–256 единиц UTF-16 | `TypeError` |
| URL для `openLink`/`openTelegramLink` | 256 символов | `TypeError` |
| Обработчиков на тип события | 16 | остальные игнорируются |
| CPU | 300 мс JS в секунду; 500 мс непрерывной задачи | задержка / виджет остановлен |
| Layout-чтения | 128 блокирующих за задачу, суммарно до 1000 мс | виджет остановлен |
| Память | 8 МБ | виджет остановлен |
| Таймеры | 64 живых | `RangeError` |
| Узлы DOM | 2000 | виджет остановлен |
| DOM-изменения | 10000 за задачу | виджет остановлен |
| Текст | 32 K единиц на значение, 48 K на документ | виджет остановлен |
| Атрибут / inline-style | 8 K единиц UTF-16 | виджет остановлен |
| CSS | 400 правил, 32 `@keyframes` | виджет остановлен |
| Canvas | 4000 команд на canvas за задачу; 2048×2048 пикселей суммарно | `RangeError` / остановка |
| `data:`-изображения | 1024×1024 пикселей | заглушка |
| Анимации из скрипта | 64 | остальные не рисуются |

| Падения подряд | 2 | остановлен до перезапуска приложения |

### 4.3. Где виджеты живут (production vs test server)

В production — **только приватный чат с ботом**. Группы, inline-режим и форварды — только тестовый сервер. Это влияет на цель проверки: линтер должен иметь режим `--target production|test`, чтобы не ругаться на фичи, которых ещё нет в проде (и наоборот — предупреждать, что они пока недоступны).

### 4.4. Профиль (кратко)

Полные списки — в [приложении D](#приложение-d-формат-файла-профиля). Принципиально важно:

- Неизвестные HTML-элементы рисуются как inline-боксы (не ошибка).
- Вырезанное **не ломает виджет**: удаляется декларация, селектор, элемент или событие, остальное работает.
- Профиль версионируется; будущие профили только **добавляют** возможности (`TelegramWidget.profile`, `isProfileAtLeast(n)`).
- `CSS.supports()` и `@supports` отвечают из профиля — это даёт способ **эмпирической калибровки** (раздел 14).

### 4.5. Уточнения из хвоста документации (блок «Writing widgets with an LLM»)

Хвост страницы (дочитано 15.11.2026) добавляет детали, важные для правил:

- **Гаптика**: свободные вызовы во время касания и 5 секунд после; без касания — одна короткая серия, затем блокировка 10 секунд (таймер не может вибрировать).
- **Off-screen `request()`**: запрос, сделанный до появления виджета, ставится в очередь и уходит при показе — «запрашивай в первых строках».
- **Формат wallet-транзакции**: ответ бота `{ valid_until, messages: [{ address, amount, payload?, stateInit? }] }`, 1–255 сообщений, `amount` — нанотоны десятичной строкой; коды отказа `REJECTED` / `BAD_REQUEST`; после `TIMEOUT` — не платить повторно, спросить бота.
- **Стоимость layout-чтений**: 128 блокирующих за задачу; они плюс ~25 мкс на каждое DOM-изменение стоят клиенту не более 100 мс в секунду.
- **Вне экрана**: `document.hidden`, таймеры не чаще 1 Гц, без анимационных кадров.
- **Приглушение вместо прозрачности**: затемнять цветом (`--tg-theme-hint-color`, `rgba()`, `fill-opacity`), никогда `opacity` (это «тяжёлый» элемент); тень без размытия бесплатна.
- **CDN-библиотеки в out-списке названы явно**: Chart.js 4, D3 7 (ничего не подгружается) — подтверждает TGW104/TGW407.
- **Двойной тап**: всегда принадлежит виджету — два `click`, затем `dblclick`.
- **Живучесть**: виджет могут уничтожить и пересоздать в любой момент; первый кадр рисовать синхронно, состояние восстанавливать из `localStorage` и state.
- **Пример-опрос** из блока — эталонный «чистый» виджет, идёт в фикстуры (раздел 15.1).

## 5. Продуктовая поверхность

### 5.1. Команды CLI

```text
widgetlint check  <файл|-|каталог> [--profile 1] [--target production|test]
                  [--format human|json|sarif] [--min-severity info|warn|error]
                  [--min-confidence heuristic|likely|certain] [--config widgetlint.toml]
widgetlint size   <файл> [--breakdown] [--budget 3800] [--format human|json]
widgetlint pack   <файл> [-o вывод] [--level safe|aggressive] [--verify]
widgetlint sim    <файл> [--scenario all|private|group|forward|preview|...]   # фаза 3
widgetlint explain TGW503                     # описание правила, примеры, ссылка на спецификацию
widgetlint rules  [--json]                    # список всех правил
widgetlint spec-watch [--against ruleset/]    # отдельный крейт, единственный с сетью
```

Коды возврата: `0` — нет находок на/выше порога; `1` — есть находки; `2` — ошибка использования/ввода; `3` — внутренняя ошибка. Порог управляется `--fail-on`.

### 5.2. Пример вывода (human)

```text

  error  TGW002  сжатый размер 4231 байт > 4096 (превышение 135)         [size]
         help: самые дорогие части: <script> 2318 B, <style> 1102 B, разметка 811 B
         spec: #what-a-widget-is
  warn   TGW100  <input> будет вырезан вместе с содержимым              строка 14:5
         help: в виджетах нет полей ввода; используйте кнопки
  warn   TGW503  request() вызван вне синхронного обработчика тапа        строка 41:9  [likely]
         help: вызывайте в click-обработчике до первого await/таймера
  info   TGW603  нижняя safe-area не учтена: время сообщения перекроет подвал
         help: padding-bottom: max(8px, env(safe-area-inset-bottom))

1 error, 2 warnings, 1 info — проверено 4 правила размера, 63 статических, профиль 1, цель production
```

## 6. Архитектура

### 6.1. Структура workspace

```text
widgetlint/
├── ruleset/
│   ├── profile-1.toml            # данные профиля (списки in/out, лимиты)
│   └── rules/                    # метаданные правил: id, severity, spec-ссылка, тексты
├── crates/
│   ├── wl-profile/               # загрузка и валидация данных профиля, встраивается в бинарь
│   ├── wl-core/                  # lint(), диагностики, конфиг, подавления, сводка
│   ├── wl-html/                  # разбор HTML (html5ever), правила HTML/SVG
│   ├── wl-css/                   # разбор CSS (lightningcss/cssparser), правила CSS и лимиты
│   ├── wl-js/                    # разбор JS (oxc), поток вызовов, правила JS/жесты/состояние
│   ├── wl-size/                  # zlib-9, разбивка, оценка повторов
│   ├── wl-pack/                  # оптимизатор (safe/aggressive), верификация
│   ├── wl-sim/                   # QuickJS + мок DOM + сценарии (фаза 3)
│   ├── wl-cli/                   # бинарь widgetlint
│   ├── wl-wasm/                  # wasm-bindgen, npm-пакет
│   ├── wl-py/                    # PyO3 + maturin
│   ├── wl-ffi/                   # C ABI, cbindgen
│   ├── wl-lsp/                   # tower-lsp
│   ├── wl-bot/                   # типы состояния, ответы, интеграция с frankenstein
│   ├── wl-macros/                # proc-macro widget!
│   └── wl-spec-watch/            # единственный крейт с сетью
├── fixtures/                     # корпус тестов: по два на правило + реальные виджеты
├── tools/                        # скрипты: сверка zlib с Python, генераторы документации
└── playground/                   # статический сайт на WASM
```

### 6.2. Конвейер `check`

```text
вход (байты) ──► валидация кодировки/NUL ──► [TGW001-004]
        │
        ├─► разбор HTML (фрагмент допускается) ──► DOM-дерево с позициями
        │        ├─ извлечение <style> блоков и style="" атрибутов
        │        ├─ извлечение <script> блоков и on*-атрибутов
        │        └─ правила wl-html (элементы, атрибуты, SVG, data:-картинки)
        │
        ├─► разбор CSS (каждый блок) ──► правила wl-css (свойства, единицы, селекторы,
        │                                 at-rules, лимиты по числу правил)
        ├─► разбор JS (каждый блок + обработчики) ──► AST ──► правила wl-js
        │                                 (API, события, поток вызовов, состояние)
        ├─► междоменные правила (CSS↔HTML↔JS): тяжёлые элементы, оценка узлов,
        │                                 тема/безопасная зона, жесты ↔ touch-action
        └─► размер: zlib-9 ──► [TGW002/003] + разбивка
                                │
              сбор → подавления (inline, конфиг) → фильтр по порогам → Report
```

Все стадии работают на **недоверенном вводе**: глубина вложенности и размер ограничены (раздел 16), паники перехватываются на границах FFI.

### 6.3. Правила как данные

Метаданные правила (ID, уровень, текст, ссылка, фаза) и списки профиля лежат в TOML и встраиваются в бинарь. Код правил — тонкий: «если элемент входит в множество `html.out.form_controls` → TGW100». Следствия:

- обновление профиля = правка данных + тесты, без переписывания анализаторов;
- `spec-watch` сравнивает данные, а не код;
- `widgetlint explain` и документация правил **генерируются** из тех же данных.

### 6.4. Профиль и цель

- `--profile N` выбирает набор данных (в v1 только `1`).
- `--target production|test` включает/выключает правила, зависящие от доступности фич (форварды, группы, inline). По умолчанию `production`.
- Виджет может объявить требуемый профиль в комментарии-директиве `<!-- widgetlint: profile>=1 -->`. Использование функций через `typeof`-проверку (`setResizeAnchor`) считается корректным.

### 6.5. Конфигурация

## 7. Модель диагностик

```jsonc
{
  "id": "TGW503",                       // стабильный идентификатор правила
  "severity": "warn",                   // error | warn | info
  "confidence": "likely",               // certain | likely | heuristic
  "message": "request() вызван вне синхронного обработчика тапа",
  "help": "Вызывайте request в click-обработчике до первого await или таймера.",
  "span": { "start": 1842, "end": 1871, "line": 41, "col": 9, "region": "script#1" },
  "spec": "https://core.telegram.org/bots/widgets#requests-to-the-bot",
  "fix": null,                          // или безопасная правка (см. ниже)
  "related": []                         // дополнительные позиции
}
```

**Уровни.**

- `error` — сервер откажет, виджет остановится или гарантированно сломан (сеть, превышение размера, нарушение жёсткого лимита).
- `warn` — клиент молча вырежет/проигнорирует, или поведение гарантированно не сработает (вне профиля, нарушение тап-правил).
- `info` — рекомендация, эвристика, неполные списки.

**Уверенность.**

- `certain` — детерминированный факт по тексту (размер, элемент из списка out).
- `likely` — структурный вывод по AST/каскаду, возможны редкие обходы.
- `heuristic` — оценка (тяжёлые элементы, зона 20 px, вертикальные драги по коду).

**Автоисправления.** Только безопасные и локальные (`--fix`): удаление комментариев, замена `#ffffff` на `#fff`. Всё остальное решает `pack`. Правка применима, только если после неё `lint` не даёт новых находок.

**Сводка.** Report содержит `summary` (число по уровням), `profile`, `target`, `schema_version`, `size` (сырой/сжатый, с разбивкой при запросе) и список диагностик, отсортированный по позиции.

| TGW804 | W | Данные ответа `answerWidgetQuery` больше 1024 байт (`WIDGET_RESULT_TOO_LARGE`) | B | M2 |
| TGW805 | I | `allowed_updates` задан и не содержит `widget_query`/`shared_widget_query` | B | M2 |
| TGW806 | W | Цель `production`, но используются группы/inline/форварды: доступны только на тестовом сервере | B | M2 |
| TGW807 | I | Нет обработки состояния «message is not modified» при правке данных: считать выполненным | B | M3 |
| TGW808 | I | `editSharedWidgetData` чаще 1 раза в секунду: нужна коалесценция | B | M3 |

### 8.10. Приоритеты первой версии

**M1 (≈45 правил):** размер, HTML/SVG, CSS, статические лимиты, базовые JS-блокировки, тема, секреты. Эти правила не требуют анализа потока и надёжны.

**M2:** потоковые правила (тап-синхронность, состояние, кошелёк, жесты), сторона бота, `pack`.

**M3:** рантайм-правила и симулятор.

## 9. Движок размера и оптимизатор

### 9.1. Точность подсчёта

Документация фиксирует: сервер сжимает HTML zlib на уровне 9; Python `zlib.compress(data, 9)` считает **ровно как сервер**; `gzip -9 -n` даёт примерно на 12 байт больше; Node.js и другие сборки zlib расходятся на десятки байт в обе стороны; возле 4096 доверять числу Python.

Следствия для реализации:

1. Использовать **настоящий zlib** (`flate2` с бэкендом `zlib`, поверх `libz-sys`), формат zlib (не raw deflate, не gzip), уровень 9, параметры по умолчанию (wbits 15, memLevel 8).
2. **Не** использовать `miniz_oxide`/`zlib-rs` как основной счётчик: байты могут расходиться.
3. Предупредить про дистрибутивы, где системный Python собран с **zlib-ng** (совместимый режим): его вывод отличается. Эталонный скрипт сверки (`tools/zlib_parity.py`) должен печатать имя и версию реализации и отказываться сверять на zlib-ng.
4. CI: параметрический тест «Rust-счётчик == Python-счётчик» на корпусе не менее 500 файлов, включая вырожденные случаи (пустой файл, 1 байт, 32768 байт, случайные данные, уже сжимаемые повторы).
5. Для WASM-сборки: собрать zlib через `cc`/`wasm32-wasi`-совместимый путь либо использовать проверенную реализацию с побайтовым паритетом; без паритета WASM-режим `size` помечается `approximate: true` и TGW002 понижается до `likely`.

### 9.2. Пороги

- `error` при `> 4096` (TGW002) и `> 32768` (TGW001).
- `warn` при `> бюджета` (TGW003), по умолчанию 3800 — так советует блок для LLM в самой документации («aim for 3800»).
- `info` в окне ±64 байта вокруг 4096 (TGW005).

### 9.3. Разбивка «куда ушли байты»

Определяем части: разметка, содержимое `<style>`, содержимое `<script>`, inline `style=""`, `data:`-URL. Для каждой части считаем **предельную стоимость**:

```text
cost(part) = C(full) − C(full без part)
```

где `C` — сжатый размер. Это честнее, чем сжимать части отдельно, потому что учитывает общий словарь. Дополнительно:

- **Поиск повторов:** n-граммы и повторяющиеся длинные подстроки (списки классов, `var(--tg-theme-…)`, повторы объявлений), оценка экономии при выносе в класс/переменную.
- **Данные, не сжимающиеся:** `data:`-изображения, длинный уникальный текст помечаются отдельно; в документации прямо сказано, что картинки в `data:` почти не сжимаются, предпочитать SVG и CSS.

### 9.4. `pack`: оптимизатор

**Цель** — минимизировать *сжатый* размер, а не сырой. Это иной критерий, чем у обычных минификаторов: иногда более длинный, но повторяющийся код сжимается лучше.

Режимы:

| Режим | Что делает |
|---|---|
| `safe` | Удаляет комментарии и лишние пробелы (с учётом `pre`, `white-space`, текста внутри inline-элементов); сокращает цвета (`#ffffff` → `#fff`); убирает значения по умолчанию; нормализует кавычки и порядок атрибутов; минификация JS без манглинга свойств; округление чисел в путях SVG по конфигу |
| `aggressive` | Всё из `safe`, плюс сокращение классов и id (только если статический анализ доказал замкнутость ссылок и нет динамической сборки селекторов), дедупликация CSS-правил, удаление неиспользуемого CSS (по опции: статически недоказуемо, т.к. DOM динамический), перестановка для лучшего сжатия |

**Инварианты (проверяются при `--verify` и в тестах):**

1. **Идемпотентность:** `pack(pack(x)) == pack(x)`.
2. **Монотонность:** набор находок `lint(pack(x))` — подмножество `lint(x)` по ID и местам (pack не выводит виджет за профиль).
3. **Монотонность размера:** сжатый размер `pack(x)` ≤ сжатого размера `x`; если оптимизация не выигрывает — вернуть исходник.
4. **Семантика:** на фазе M3 — равенство снимков DOM в симуляторе для набора сценариев; до этого — только консервативные преобразования.

Минификатор JS — на базе `oxc` (парсер/минификатор); для CSS — `lightningcss` в **режиме без преобразования целей**, чтобы не вводить функции вне профиля (например, он не должен «модернизировать» синтаксис в то, что клиент вырежет). Любой вывод проходит повторный `lint`.

## 10. Статический анализ: детали

### 10.1. HTML

- Парсер: `html5ever` в режиме **фрагмента** (документ без `<html>`/`<body>` допустим по спецификации виджетов); позиции узлов сохраняются.
- Извлекаются: `<style>`-блоки, `<script>`-блоки (без `src`), атрибуты `style`, `on*`-обработчики (они исполняются в песочнице, значит анализируются как JS).
- Подсчёт узлов: элементы + текстовые узлы + комментарии (по определению лимита). Это **нижняя оценка**: JS создаёт узлы динамически, в диагностике указывать «минимум».
- Списки профиля применяются по имени элемента/атрибута; неизвестное — TGW110 (`info`).
- Учитывать, что парсер HTML исправляет разметку; позиции диагностик нужно отображать в исходном тексте, а не в нормализованном.

### 10.2. CSS

- Парсер: `lightningcss` (разбор с сохранением позиций) или `cssparser`; обход правил, деклараций, селекторов, at-rules, значений.
- Счётчики для лимитов: число **правил**, число `@keyframes`, длина значений.
- Нормализация значений для сопоставления с профилем: единицы, функции цвета, имена фильтров, значения `overflow`/`position`/`display`.
- Каскад: для TGW602/TGW603/TGW604 нужен ограниченный анализ — какие правила попадают на `html`/`body`/`.footer`. Полный каскад не строится: используется консервативное сопоставление селекторов; при сомнении — `heuristic`.
- «Тяжёлые» элементы (TGW305): считаем элементы, к которым статически применимы `opacity<1`, `filter`, `backdrop-filter`, `box-shadow` с размытием, их анимации; псевдоэлементы `::before`/`::after` считаются отдельными. Результат — оценка с доверительным интервалом, уровень `heuristic`.
- Неизвестное свойство/значение вне списков «In/Out» → TGW216 (`info`), поскольку списки неполны.

### 10.3. JavaScript

- Парсер: `oxc_parser` (ES2023+), построение AST со спанами.
- Обязательно разбирать: все `<script>`-блоки, `on*`-атрибуты, а также `new Function`/`eval` с **литеральной** строкой (иначе — `info` «динамический код, анализ невозможен»).
- **Таблица API.** Из профиля строятся множества: запрещённые глобальные (сеть, диалоги, навигация), методы объектов (`navigator.*`, `canvas ctx.*`), свойства. Сопоставление по имени с учётом псевдонимов вида `const f = fetch` (простое отслеживание присваиваний на уровне модуля).
- **Анализ «тап-синхронности»** (TGW503–505, основа M2):
  1. Определить **входные точки тапа**: обработчики `click`, `pointerup`, `onclick`, `dblclick` (и `addEventListener` с литеральным типом события).
  2. Построить **ограниченный граф вызовов** внутри файла: локальные функции, стрелки, методы объектов-литералов; глубина ограничена (по умолчанию 8).
  3. Привилегированные вызовы (`TelegramWidget.request`, `openLink`, `openTelegramLink`, `copyText`, `wallet.sendTransaction`, `wallet.signData`) считаются **синхронными**, если путь от входной точки к вызову не пересекает: `await`, `.then/.catch/.finally`-колбэк, `setTimeout/setInterval/requestAnimationFrame`, `queueMicrotask`.
  4. Исключение: допустимый вызов кошелька в `.then` непосредственно на результат `request(..., {wallet:true})` (в документации это основной сценарий оплаты: ответ на вызов с тапом открывает окно в 10 секунд). Это правило TGW713, оно отдельное.
  5. Если путь не удалось проследить (передача функции вне файла, динамические ключи) — диагностику не выдавать или давать `heuristic`.
  6. `pointerdown` как входная точка для привилегированных вызовов — отдельное предупреждение (TGW504).
- **Анализ жестов** (TGW506–509): корреляция JS-обработчиков `pointermove`/`pointerdown` с CSS `touch-action` на целевом элементе и его предках. Выбор элемента — по литеральным селекторам `getElementById`/`querySelector`; иначе `heuristic`.
- **Анализ состояния** (TGW700–703, 708): обращения к `TelegramWidget.chatData`/`publicData`, оборачивание `JSON.parse` в `try`, проверки `=== null`/`!x`, регистрация `onEvent('chatDataChanged', …)`.
- **Секреты** (TGW714): регулярные выражения форматов токенов (формат токена бота `\d{8,10}:[A-Za-z0-9_-]{35}`, типичные префиксы ключей, PEM-блоки), плюс энтропийная эвристика для длинных строк. Уровень `likely` для известных форматов, иначе `heuristic`.

### 10.4. Междоменные правила

- Жесты: JS-обработчик ↔ CSS `touch-action`.
- Тема/безопасная зона: `body`/`footer`-правила ↔ `env(safe-area-inset-bottom)`, `--tg-content-safe-area-corner-*`.
- Тяжёлые элементы: CSS-эффекты ↔ структура HTML (кратность элементов).
- `allow_queries` ↔ использование `request()` (сторона бота + JS).

### 10.5. Подавление ложных срабатываний

1. Инлайн-директивы и конфиг (раздел 6.5).
2. Уровень уверенности: по умолчанию вывод `likely` и `certain`.
3. `--strict` показывает всё, включая `heuristic`.
4. Каждое правило имеет страницу с примерами «срабатывает / не срабатывает» (генерируется из фикстур).

## 11. Симулятор (фаза 3)

**Назначение.** Ловить то, что статикой не поймать: рантайм-лимиты и поведение в разных окружениях.

**Основа.** `rquickjs` (QuickJS для Rust) + собственный минимальный DOM, реализующий **только** поддерживаемое профилем подмножество API. Всё, что не реализовано в симуляторе, помечается как «не поддержано симулятором», а **не** как баг виджета.

**Что считается.**

| Метрика | Лимит |
|---|---|
| Число узлов | 2000 |
| DOM-изменения за задачу | 10000 |
| Живые таймеры | 64 |
| CPU за задачу | 500 мс (через interrupt handler по таймеру/числу инструкций) |
| Память | 8 МБ (`set_memory_limit`) |
| Команды canvas за задачу | 4000 на canvas |
| Layout-чтения за задачу | 128 |
| Обработчики на событие | 16 |
| Вызовы сетевых API | любой — `NetworkDisabledError` и находка |

**Матрица сценариев.**

| Измерение | Значения |
|---|---|
| Окружение | приватный чат; группа; форвард статического; форвард общего; превью; отправлен через бота |
| Тема | light; dark |
| Ширина пузыря | 320; 430; 600 |
| Подпись | нет; сверху; снизу (меняет safe-area) |
| Состояние | `null`; примерное (из файла фикстуры) |
| Профиль/цель | production; test |

**Проверки.** Нет необработанных исключений; нет сетевых вызовов; все привилегированные вызовы в запрещённых окружениях обработаны (`NOT_ALLOWED` не приводит к падению); обработчики `chatDataChanged`/`publicDataChanged` выполняются без ошибок на примерах состояния; снимок DOM детерминирован (для `pack --verify`).

**Чего симулятор не делает.** Не считает раскладку и итоговую высоту пузыря (нужен рендерер); для TGW609 доступны только приближённые оценки. Опционально — режим «визуальный предпросмотр» через headless-браузер с заглушкой `TelegramWidget`, но с явной пометкой, что это не клиент Telegram (документация сама предупреждает: браузер рисует то, что клиенты вырезают, и не применяет лимитов).

**Сложность и риск.** Минимальный DOM на Rust — значительный объём работы. Поэтому фаза 3, с жёсткими рамками: сначала счётчики лимитов и мок `TelegramWidget`, затем уже DOM-снимки.

## 12. Поставка и работа с другими языками

### 12.1. Общий принцип

Одно ядро `wl-core` → единый JSON-контракт → разные оболочки. Контракт `Report` версионируется (`schema_version`), внутри мажорной версии изменения только добавляющие; идентификаторы правил не переиспользуются никогда.

### 12.2. Каналы

| Канал | Аудитория | Технология | Фаза |
|---|---|---|---|
| CLI | все; любой язык через subprocess; CI | `wl-cli`, форматы human/json/sarif | M1 |
| SARIF | GitHub code scanning, аннотации в PR | вывод `--format sarif` | M1 |
| WASM + npm | Node, grammY, telegraf, браузер, веб-редакторы | `wasm-bindgen`/`wasm-pack` | M1 (песочница), M2 (npm) |
| Онлайн-песочница | все: вставил HTML — увидел отчёт и счётчик байт | статический сайт на WASM | M1 |
| PyO3-колесо | aiogram, python-telegram-bot | `maturin`, abi3-колёса | M2 |
| C ABI | Go, C/C++, Java/Kotlin (JNI), Swift, .NET | `wl-ffi` + `cbindgen` | M2 |
| GitHub Action | CI | composite-action вокруг CLI | M2 |
| pre-commit | локальная разработка | хук вокруг CLI | M2 |
| LSP | любой редактор | `tower-lsp`, диагностики в реальном времени | M3 |
| Rust-крейт | Rust-боты | `wl-core` как библиотека | M1 |

### 12.3. API границ

**WASM (TypeScript):**
```ts
import { lint, size, pack } from "@widgetlint/wasm";
const report = lint(html, { profile: 1, target: "production" });
```

**Python:**
```python
import widgetlint
report = widgetlint.lint(html, profile=1, target="production")   # dict по схеме Report
widgetlint.size(html)                                              # {"raw": ..., "zlib9": ...}
```

**C ABI:**
```c
char* wl_lint_json(const char* html, const char* config_json);
char* wl_size_json(const char* html);
void  wl_free(char* ptr);
const char* wl_version(void);
```
Все функции FFI перехватывают паники; ошибки возвращаются как JSON `{ "error": {...} }`, а не падением процесса.

### 12.4. Условие паритета

CI-гейт «**одинаковость оболочек**»: один и тот же корпус фикстур прогоняется через CLI, WASM (Node), Python-колесо и C ABI; сравнивается JSON **побайтово**. Расхождение — блокирующая ошибка. Единственное допустимое исключение — режим `approximate` размера в WASM (см. 9.1), который выводится явным полем.

### 12.5. Размеры и версии

- Бюджет размера WASM-бандла фиксируется и отслеживается в CI (цель на старте: минимизировать, пороги определить по первой сборке; зависимости — `html5ever`, `lightningcss`, `oxc` — тяжёлые, возможен отказ от части ради размера).
- Единая версия во всех пакетах; релиз — одним тегом; changelog содержит изменения набора правил (добавлено/изменён уровень/удалено).
- MSRV указывается и проверяется в CI.

## 13. Rust-слой: макрос, типы состояния, роутер

Над языково-независимым ядром — слой, который нужен только Rust-разработчикам и даёт то, чего нет в других языках.

### 13.1. Макрос `widget!`

```rust
const ORDER: Widget = widget!("widgets/order.html");          // проверка при компиляции
```
- Читает файл при компиляции, запускает `wl-core::lint` с профилем и целью из `Cargo.toml` (`[package.metadata.widgetlint]`).
- `error` → `compile_error!` с переносом позиций; `warn` → предупреждение компилятора (по настройке можно сделать ошибкой).
- Встраивает уже **оптимизированный** HTML (`widget!("…", pack = "safe")`) и константу сжатого размера, чтобы ограничения проверялись `const`-утверждением.

### 13.2. Типизированное состояние

```rust
struct Game { board: [u8; 9], turn: u8, rev: u32 }
let data: ChatData<Game> = ChatData::new(&game)?;   // Err, если сериализация > 1024 байт
```
- `ChatData<T>`, `PublicData<T>`: проверка 1024 байта, UTF-8, отсутствие NUL — на этапе сериализации (`TGW801`).
- Поле ревизии (`rev`) как рекомендуемый паттерн (TGW708).
- `AnswerData` (≤ 1024 байт, TGW804).

### 13.3. Роутер запросов (интеграция с вариантом A)

- Типы и роутер для `widget_query` и `shared_widget_query` поверх существующих Bot API-клиентов (в первую очередь `frankenstein`; поддержка 10.4 пока не подтверждена — проверить и по возможности отправить PR вместо отдельного фреймворка).
- Ключ идемпотентности «один голос на пользователя» и платёжные действия — по паре **(`widget_id`, `from.id`)**: так сказано в документации, потому что запрос из форварда не содержит чата и сообщения.
- Ответ **на каждый** запрос в 15 секунд (в документации — иначе `TIMEOUT` на стороне виджета).
- Коалесценция правок общего состояния (≤ 1 в секунду).
- Обработка состояния «message is not modified» как успеха.
- Проверка платежей: роутер даёт каркас «получили `sent_transaction` → проверили в блокчейне → ответили». Документация требует проверять отправителя, получателей, суммы и исход **по цепочке**, а не по одному хешу; реализация этой проверки зависит от выбранного TON-клиента и в v1 — лишь интерфейс (trait).
- Проверка подписи (`sign_data`): интерфейс для проверки подписи публичным ключом кошелька и привязки ключа к адресу.

### 13.4. Мок для тестов

`MockWidgetClient`: эмулирует `widget_query` (разные места: приват, группа, форвард, inline), время ответа, лимит запросов, `TIMEOUT`; позволяет тестировать роутер без реального Telegram.

## 14. Следилка за спецификацией и калибровка по реальным клиентам

### 14.1. `spec-watch`

Отдельный крейт `wl-spec-watch` (единственный с доступом в сеть, не входит в ядро).

1. Скачивает `/bots/widgets.md` и страницу changelog Bot API.
2. Разбирает структурированные части: таблицу лимитов, списки «In/Out» профиля, таблицы прав и ошибок.
3. Нормализует и сравнивает с `ruleset/profile-N.toml`; хранит хеш источника в самом наборе правил (`spec_snapshot`).
4. При расхождении открывает issue с диффом (в CI по расписанию, ночью).
5. Отдельный сигнал — **появление нового профиля** (`profile 2`) или новых методов виджетов в changelog.

### 14.2. Калибровка: зонд-виджет

Документация утверждает: `CSS.supports(property, value)` и `@supports` **отвечают из профиля** — `true`, только если приложение сохраняет декларацию. Это позволяет проверить набор правил на реальных клиентах.

**Зонд** — служебный виджет, который перебирает матрицу «свойство/значение» и «API», записывает результаты и выводит их на экран (и, при необходимости, отправляет боту по частям по 64 байта через несколько тапов). Прогон на тестовом сервере и в production-клиентах (iOS, Android, macOS, Desktop, Web) даёт:

- подтверждение списков «Out» и «In» на реальных клиентах;
- выявление расхождений между платформами (документация утверждает одинаковость);
- данные для полей `confidence` правил.

Результаты прогона сохраняются как артефакты в репозитории (`calibration/<дата>/<платформа>.json`), а регрессии ловит CI.

### 14.3. Ограничение

Зонд проверяет то, что отвечает `CSS.supports`, и то, что можно наблюдать из JS. Побочные эффекты вырезания (например, поведение жестов или размера) надо проверять вручную по протоколу из раздела «Testing in Telegram» официальной документации (приват, группа с двумя аккаунтами, inline, форварды, обе темы, исходящий пузырь, крупный шрифт, RTL, старый телефон).

## 15. Стратегия тестирования

### 15.1. Корпус фикстур

- Для **каждого** правила не менее двух фикстур: «срабатывает» и «не срабатывает» (граничный случай). CI-гейт: правило без обеих фикстур не проходит.
- Файлы: `fixtures/<rule>/<name>.html` + `<name>.expected.json`.
- Сквозные «золотые» файлы для реальных виджетов: пример «Order #1042» из документации, пример-опрос из блока «Writing widgets with an LLM» (официальный эталон), простые игры/опросы/тикеры (с учётом лицензий; для чужих работ — только после согласия авторов).
- Критерий «0 ошибок»: все примеры из официальной документации должны проходить линтер без `error`.

### 15.2. Уровни тестов

| Уровень | Что проверяет | Инструменты |
|---|---|---|
| Юнит-тесты | каждый анализатор, парсеры данных профиля | `cargo test` |
| Snapshot | стабильность вывода диагностик | `insta` |
| Паритет zlib | Rust-счётчик == Python-счётчик на ≥ 500 файлах | скрипт + CI |
| Property-based | идемпотентность `pack`, монотонность `lint(pack(x)) ⊆ lint(x)`, отсутствие паник на случайном вводе | `proptest` |
| Фаззинг | HTML/CSS/JS-пути, FFI-границы, загрузчик профиля | `cargo-fuzz` (в CI — короткие прогоны, ночью — длинные) |
| Паритет оболочек | CLI == WASM == Python == C ABI побайтово | матрица CI |
| Производительность | ≤ 50 мс на 32 КБ (см. раздел 16) | `criterion`, пороги в CI |
| Калибровка | зонд-виджет на реальных клиентах | ручной/полуавтоматический прогон |
| Дрейф спецификации | расхождение набора правил с документацией | `spec-watch` по расписанию |

### 15.3. Метрики качества

- Доля ложных срабатываний на корпусе «чистых» реальных виджетов — цель близка к нулю для `certain`/`likely`.
- Покрытие правил фикстурами — 100%.
- Покрытие кода — измеряется, но не самоцель.

### 15.4. CI

Матрица: Linux/macOS/Windows × stable Rust + MSRV; отдельные задания: WASM-сборка и тест в Node, сборка колёс Python (manylinux/macOS/Windows), проверка размера WASM, ночной фаззинг и `spec-watch`.

## 18. Роадмап и критерии приёмки

Оценки рассчитаны на сфокусированную работу одного разработчика с готовой инфраструктурой CI; они ориентировочные и пересматриваются после M0.

### M0 — основа (дни 1–2)

- Репозиторий, workspace, CI-скелет, лицензия.
- Данные `profile-1.toml` из документации; загрузчик с валидацией.
- `size` с настоящим zlib; скрипт сверки с Python.
- **Приёмка:** `size` совпадает с Python на ≥ 100 файлах; данные профиля проходят схему.

### M1 — линтер MVP (неделя 1)

- Правила TGW0xx, TGW1xx, TGW2xx, TGW3xx (статические), базовые TGW4xx/TGW5xx (поиск запрещённых API/событий), TGW6xx, TGW714, TGW704, TGW709.
- CLI: `check`, `size`, `explain`, `rules`; форматы human/json/sarif; конфиг и подавления.
- WASM-песочница на GitHub Pages: вставка HTML → отчёт и счётчик байт.
- **Приёмка:** все правила M1 с двумя фикстурами; все примеры из официальной документации без `error`; песочница работает в Chrome, Firefox, Safari; релиз `v0.1`.

### M2 — глубина и поставка (неделя 2)

- Анализ потока JS: TGW503–509, TGW700–712, TGW306–307, сторона бота TGW8xx.
- `pack` (режимы safe/aggressive) с верификацией инвариантов.
- Оболочки: npm-пакет, PyO3-колесо, C ABI; GitHub Action и pre-commit.
- `spec-watch` в ночном CI.
- Паритет оболочек: CLI == WASM == Python == C ABI побайтово.
- **Приёмка:** паритет-гейт зелёный; `pack` идемпотентен и монотонен на корпусе; `v0.2`.

### M3 — симулятор, LSP, Rust-слой (позже)

- `wl-sim`: счётчики лимитов, мок `TelegramWidget`, матрица сценариев.

- **Приёмка:** симулятор ловит все синтетические нарушения лимитов из фикстур; LSP показывает диагностики в VS Code и Neovim; `v0.3`.

### Метрики успеха (ориентиры, пересматриваются)

- Количество установок/запусков песочницы, звёзды, упоминания в каналах и чатах разработчиков ботов.

- Доля пользователей вне Rust (npm/PyPI против crates.io).

### Приложение F. Глоссарий

| Термин | Значение |
|---|---|
| Виджет | HTML-документ, исполняемый в песочнице QuickJS внутри пузыря сообщения |
| Профиль (profile 1) | Контракт между виджетами и клиентами: что отрисовывается одинаково во всех приложениях |
| Статический виджет | Код и состояние хранятся в сообщении, форвард копирует снимок |
| Общий виджет (shared) | Один объект на сервере с идентификатором; общее состояние для всех сообщений и форвардов |
| `chat_data` | Состояние, привязанное к одному сообщению |
| `public_data` | Общее состояние, видимое везде, где показан виджет |
| `widget_query` / `shared_widget_query` | Апдейты бота с запросом из виджета (оригинал / форвард общего виджета) |
| Тап-синхронность | Требование вызывать привилегированные методы синхронно в обработчике настоящего тапа |
| Safe-area | Полоса внизу, которую приложение закрывает временем сообщения |
| Тяжёлый элемент | Элемент с размытой тенью, `filter`, `backdrop-filter`, `opacity < 1` или их анимацией |
| Предельная стоимость | Прирост сжатого размера от части документа: `C(целое) − C(целое без части)` |
